MINE HAUL CYCLE

Open-pit haul truck: kinematics in MATLAB

One repo, one story. A loaded truck climbs a pit ramp, dumps, and returns empty. You analyse the surveyed path like GPS ride data, then throw that data away and prescribe the motion yourself with a piecewise speed law, then add a conveyor discharge as a projectile. There is no mark scheme. The test is whether the scripts still run in six months and whether you can defend every number they print.

The engineering picture

An open pit is a hole with a spiral road cut into its wall. A shovel loads a truck on the pit floor. The truck climbs the ramp to a dump or crusher on the surface, tips its load, and drives back down empty to queue for the shovel again. That loop is the haul cycle, and its duration decides how much rock the mine moves per hour. Everything in this project is an attempt to predict that number from geometry and kinematics.

Three facts drive the whole model:

  • Loaded uphill is slow, empty downhill is fast. The same road produces two very different speed profiles. Our loaded truck tops out around 25 km/h, the empty one around 40 km/h.
  • The ramp is long and gently graded, not a cliff. Grade is rise over horizontal run, quoted as a percentage. Mine ramps sit near 8–10%. Ours peaks at 8.24% on the switchback.
  • Waiting is part of the cycle. Spotting under the shovel and tipping at the pad cost real minutes. If you model only the driving, your predicted productivity will be far too optimistic.

Scope discipline for the first 40 days

This is a kinematics model: position, velocity, acceleration, path length, grade, and time. It contains no forces, no rolling resistance, no engine torque curve, no fuel burn. That restraint is deliberate — you are learning MATLAB, and a model with five unknown coefficients teaches you less than a model with none.

The MATLAB surface you will actually use is small. If you can drive these confidently the rest of first-year computing is comfortable:

Truck constants

Put these in one function that returns a struct. Never retype a number inside a plot title or a formula — if you later change the payload, exactly one line should change.

function p = truck_params()
% Constants for the mine haul-cycle model. All SI unless noted.
p.g            = 9.81;      % m/s^2
p.v_loaded_max = 25/3.6;    % m/s   ~25 km/h, loaded on grade
p.v_empty_max  = 40/3.6;    % m/s   ~40 km/h, empty
p.a_accel      = 0.35;      % m/s^2 gentle haul-truck start
p.a_brake      = -0.50;     % m/s^2 service braking
p.t_dump       = 40;        % s     tipping at the pad
p.t_load       = 50;        % s     spotting and loading
p.payload_t    = 180;       % t     rated payload
end

The five stages

Each stage below states why it exists, exactly what to compute, what the figure must contain, the numbers you should land on, and the mistakes that catch people. Target numbers are there so you can catch a bug on the same day you write it. Never hard-code them — if your script prints them because you typed them in, you have learned nothing.

Stage 0 — Repo shape and the habit of committing

Before any physics. The point of this stage is that in six months you will open a folder you have forgotten, and it must explain itself. A flat pile of untitled3.m files fails that test.

Stage 1 — Measure the road: path, grade, distance, speed

You are handed coordinates and must turn them into the quantities an engineer actually quotes: how long is the haul, how steep is the worst pull, how fast was the truck going. This is the same analysis as Project 1 Parts A–B with a mine's numbers, and it is the single most transferable skill in the project — every GPS, survey or logger dataset you meet later is processed exactly this way.

1a — 3-D path

Plot the centreline with plot3(E,N,z). Overlay the eight sample points as markers so the reader can see the sampling, and put a distinct marker plus a text label on the loader and the dump pad. Label all three axes with units, add grid on, and give it a title naming the mine feature, not the variable ("Haul ramp centreline, pit floor to ROM pad").

1b — Grade

Grade is rise over horizontal run, not over slope distance. For each interval:

\[\Delta s_{xy,i}=\sqrt{(\Delta E_i)^2+(\Delta N_i)^2},\qquad G_i = 100\,\frac{\Delta z_i}{\Delta s_{xy,i}}\ \ (\%)\]

There are eight samples and therefore seven grades. Grade belongs to an interval, not to an instant, so plot it at interval mid-times (or use a stairstep). On one figure use yyaxis left for elevation against time and yyaxis right for grade against time, so the reader sees that the steepest pull coincides with the switchback.

1c — Distance and speed

Segment length in three dimensions, then a running total:

\[\Delta s_i=\sqrt{(\Delta E_i)^2+(\Delta N_i)^2+(\Delta z_i)^2},\qquad s_k=\sum_{i=1}^{k}\Delta s_i\]

Use cumsum, and remember \(s\) must start at zero, so the cumulative vector needs a leading zero to stay the same length as the samples. Convert segment speeds \(v_i=\Delta s_i/\Delta t_i\) to km/h for the plot, because that is how a mine talks about truck speed. Produce two plots: speed against time, and speed against cumulative distance. The second is the one a mine planner actually reads, because it shows where on the road the truck is slow.

1d — Printed summary

Use fprintf with sensible field widths and units, not bare disp. Report total path length in metres and kilometres, total rise, mean climb speed in km/h, the steepest grade and which segment it belongs to.

Deliverable. s1_path3d.m, s1_grade.m, s1_distance_speed.m, a reusable functions/path_metrics.m that takes E,N,z and returns segment lengths, cumulative distance and grades, plus four saved figures in figures/.
Your numbers should be: total path length 545.0 m, total rise 35 m, mean climb speed 7.0 km/h, steepest grade 8.24% on segment 4 (the switchback, 259 m to 332 m along the road). Segment speeds should run between 4.9 and 8.3 km/h. If your total is 543.9 m you have used horizontal distance somewhere; if it is 546 m you have probably summed with a stray element.
Traps. Off-by-one is the whole of this stage: diff returns \(n-1\) values, so plotting a 7-element grade against an 8-element time vector will error, and "fixing" it by padding with a zero silently invents a flat segment. The switchback has a negative \(\Delta E\), so anything using \(|\Delta E|\) or assuming monotonic easting gives a wrong length. Finally, do not compute speed by differentiating position components separately and adding them — take the magnitude of the displacement first.

Stage 2 — Drive it yourself: the piecewise speed law

Stage 1 described one climb that happened. Stage 2 asks the design question: if a truck accelerates gently, runs at its safe maximum, then brakes to rest at the pad, how long does the climb take? This is where SUVAT stops being exam furniture and becomes a generator of arrays.

Take the total path length \(S\) from Stage 1 and treat the road as a one-dimensional coordinate \(s\) from 0 to \(S\). Three phases:

\[t_{\text{acc}}=\frac{v_{\max}}{a_{\text{acc}}},\quad s_{\text{acc}}=\frac{v_{\max}^2}{2a_{\text{acc}}},\qquad t_{\text{br}}=\frac{v_{\max}}{|a_{\text{br}}|},\quad s_{\text{br}}=\frac{v_{\max}^2}{2|a_{\text{br}}|}\]

\[s_{\text{cruise}}=S-s_{\text{acc}}-s_{\text{br}},\qquad t_{\text{cruise}}=\frac{s_{\text{cruise}}}{v_{\max}}\]

What to compute

  1. The six phase quantities above, printed with units.
  2. A guard: if \(s_{\text{acc}}+s_{\text{br}} > S\) there is no room to reach \(v_{\max}\), and the truck runs a triangular profile with a reduced peak \(v_{\text{peak}}=\sqrt{2Sa_{\text{acc}}|a_{\text{br}}|/(a_{\text{acc}}+|a_{\text{br}}|)}\). Write this as an if even though our ramp does not trigger it, then prove it works by calling the function with \(S=80\) m.
  3. Arrays: build \(t\), \(s(t)\), \(v(t)\), \(a(t)\) with linspace over each phase and concatenate. Keep the phases in one consistent time base so the joins are continuous.
  4. One figure, three stacked subplot panels sharing a time axis: distance, speed, acceleration. Acceleration is a step function — positive, zero, negative — and it should look like one.
Deliverable. functions/piecewise_motion.m with signature [t,s,v,a] = piecewise_motion(S, vmax, a_acc, a_brake), plus scripts/s2_loaded_climb.m that calls it with Stage 1's \(S\) and plots the three panels.
Your numbers should be: \(t_{\text{acc}}=19.8\) s over 68.9 m, cruise 61.6 s over 427.9 m, braking 13.9 s over 48.2 m, giving a loaded climb of 95.3 s. Check the area: trapz(t,v) must return 545 m to within rounding. The final element of your s array must equal \(S\), not 544 or 546.
The interesting discrepancy. The surveyed climb took 280 s; your model says 95 s. Do not "fix" this. Write two or three sentences in the memo explaining it: a loaded truck genuinely cannot hold 25 km/h up a sustained 8% grade, and the real trace also contains queueing, gear changes and cornering at the switchback. Then say what you would change — a grade-dependent speed limit is the honest next model. Recognising that a clean model disagrees with data, and saying why, is the actual engineering skill in this project.
Coding traps. Sign errors on braking (feed the function \(-0.50\) but use \(|a|\) in the distance formula). Concatenating phases without offsetting each phase's start time, which gives a sawtooth. And building \(s\) by cumsum(v)*dt with an uneven dt — use the analytic SUVAT expression per phase instead.

Stage 3 — The full cycle and the number the mine cares about

Now assemble a whole loop and convert it into productivity. This is the stage where the project stops being a plotting exercise and starts answering a business question.

What to compute

  1. The empty return over the same 545 m at \(v_{\text{empty,max}}\), same acceleration magnitudes. Reuse piecewise_motion unchanged — if you find yourself copy-pasting it and editing a number, the function's arguments are wrong.
  2. Insert the two waits as genuine constant-position, zero-velocity intervals in the arrays, not as a number added at the end. The velocity array must actually contain the flat sections, because you will integrate it as a check.
  3. Total cycle time \(T_{\text{cycle}}\), reported in both seconds and minutes.
  4. Productivity \(\text{tph} = 3600\,\times\,\text{payload}/T_{\text{cycle}}\), and trucks-per-hour \(3600/T_{\text{cycle}}\).
  5. One cycle figure matching Diagram 3: speed against time across the whole loop, with the two waits shaded and annotated, and a legend distinguishing loaded from empty.
Deliverable. functions/cycle_time.m returning a struct of the four phase durations and the total, scripts/s3_full_cycle.m, and the annotated cycle figure.
Your numbers should be: empty return 76.0 s (31.7 s accelerating, 22.1 s cruising, 22.2 s braking), \(T_{\text{cycle}} = 95.3+40+76.0+50 = \mathbf{261.4\ s}\), which is 4.36 minutes, about 13.8 loads per hour and roughly 2 480 t/h. Sanity-check that the empty return is faster than the loaded climb but not by the full 40/25 speed ratio — it spends proportionally more of its trip accelerating and braking, which is a genuinely interesting result worth one line in the memo.
Trap. 2 480 t/h is optimistic and you should say so. It assumes no queue at the shovel, no traffic on the ramp, no shift change, no rain. Real mines apply an availability and utilisation factor. Note in the memo what your figure would become at 80% utilisation.

Stage 4 — Conveyor discharge as a projectile

At the dump the ore goes onto a conveyor and leaves the head pulley as a free-flying stream into a bin. Horizontal and vertical motion are independent, sharing only time — the same structure as every projectile in Guide 4, now written once as a reusable function instead of solved by hand for a mark.

Ore leaves at \(v_0 = 3.5\) m/s, belt inclined at \(\theta = 18^\circ\) above horizontal, lip \(h = 4.0\) m above the bin floor, \(g = 9.81\) m/s², air resistance ignored.

\[x(t) = (v_0\cos\theta)\,t,\qquad y(t) = h + (v_0\sin\theta)\,t - \tfrac12 g t^2\]

Landing is the positive root of \(y(t)=0\):

\[t_f = \frac{v_0\sin\theta + \sqrt{(v_0\sin\theta)^2 + 2gh}}{g}\]

What to compute

  1. Solve \(t_f\) analytically with the quadratic formula, then build tv = linspace(0,tf,200) and the vectorised \(x\) and \(y\) arrays. Both are one-liners; if you find yourself writing a for loop here, stop and vectorise.
  2. Plot \(y\) against \(x\) with equal axis scaling (axis equal) so the trajectory is not visually distorted, mark the lip and the landing point, and draw the bin floor as a horizontal line at \(y=0\).
  3. Print time of flight, horizontal range, and apex height with units.
  4. Verify numerically against the analytic values: the maximum of your \(y\) array should match \(h+(v_0\sin\theta)^2/(2g)\) to within the resolution of your 200-point grid. State that agreement in the printout — this is how you learn to trust your own arrays.
  5. Overlay a second belt speed (try 4.5 m/s) on the same axes with a legend, and comment on whether the bin at 3.4–4.5 m from the lip still catches the stream.
Deliverable. functions/projectile_xy.m taking \((v_0,\theta,h,g)\) and returning \(t,x,y\) plus a struct of flight time, range and apex; scripts/s4_conveyor.m producing the two-speed overlay figure.
Your numbers should be: \(v_x = 3.329\) m/s, \(v_y = 1.082\) m/s, time of flight 1.020 s, range 3.40 m, apex 4.060 m reached only 0.37 m from the lip. At 4.5 m/s the range grows to roughly 4.4 m — enough to matter for bin placement, which is exactly the point of running the second case.
Traps. MATLAB trigonometry takes radians: use cosd(18)/sind(18) or convert with deg2rad. Taking the negative root of the quadratic gives a physically meaningless time before launch. And launching from \(y=h\) rather than \(y=0\) is the whole difference between a 3.4 m range and a nonsense 0.7 m one — the ore starts 4 m up.

Stage 5 — File I/O, one-command reproducibility, and the memo

The last stage converts a folder of working scripts into something a stranger — including future you — can run and understand. This is what makes the six-month keep-warm cheap.

What to build

  1. Write data/ramp_climb.csv with a header row t_s,E_m,N_m,z_m using writematrix, then delete the hard-coded vectors from your scripts and read the file with readmatrix. Handle the header row correctly rather than eyeballing the offset.
  2. Save every figure to figures/ with saveas (or exportgraphics for tidier margins). Consistent filenames: fig_s1_path3d.png and so on.
  3. run_all.m at the top level: addpath, then call Stages 1 through 4 in order, regenerating every figure and printing every summary. It must work after clear all; close all in a fresh session.
  4. memo.md, roughly one page. Not a lab report — a set of defensible statements.

What the memo must say

  • Haul length, total rise, and the steepest grade with its location on the road.
  • Modelled loaded climb, empty return, and total cycle time, with the productivity figure and an honest note on what it ignores.
  • The 95 s versus 280 s discrepancy, with your explanation and the model change you would make next.
  • Conveyor range and flight time, and one sentence on bin placement tolerance.
  • One thing you would measure on a real ramp to improve the model, and why that measurement and not another.
Deliverable. run_all.m, the CSV, all figures on disk, and memo.md committed.
Done when you can close MATLAB, reopen it, type run_all, and get every figure and every printed line with no manual steps and no errors. That single command is the deliverable that matters most in six months.

Six-month extensions — one feature per month

After the 40 days the model is frozen. During the keep-warm you add exactly one feature a month in two short sessions a week. The rule is that run_all.m must still work at the end of every month.

  1. Loaded versus empty comparison. Both speed profiles on one set of axes with a legend, and a printed \(\Delta T\). Cheap, and it forces you back through the function signatures.
  2. A second, gentler ramp. Longer path, lower maximum grade, new CSV — no new functions at all. Compare tonnes per hour and decide which ramp a mine should build. If you have to edit path_metrics.m to load it, Stage 5 was not finished properly.
  3. Waste-dump projectile. A second discharge with different \(v_0\), \(\theta\) and \(h\), reusing projectile_xy.m untouched.
  4. A shift of twenty cycles with a random extra dump wait between 0 and 15 s using rand. Histogram the resulting tonnes per hour, and report mean and spread. This is your first taste of variability in an engineering estimate.
  5. Animation. A truck marker moving along \(E(s),N(s)\) with drawnow or comet3, driven by the Stage 2 time base rather than the sample points.
  6. Freeze month. Run run_all.m on a clean session. If it fails, the entire month's job is making it run again — not adding a seventh feature.
If you want to go further after that, the honest next step is a grade-dependent speed limit: cap \(v_{\max}\) as a function of the local grade so the modelled climb moves toward the surveyed 280 s. That single change turns a kinematics toy into something resembling a real haulage simulation, and it uses only what you already built.
